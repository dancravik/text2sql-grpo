# Зафиксированные данные эксперимента v1

Главный файл — `splits/v1.json`. Он хранится в Git вместе с кодом, а исходные
датасеты остаются в `DATA_DIR`. Один и тот же manifest используется во всех
Kaggle-сессиях и во всех ветках обучения: исходная Qwen3.5-2B, SFT и GRPO.

## Назначение выборок

| Имя в коде | Источник | Примеров | Баз | Использование |
|---|---|---:|---:|---|
| `train` | Часть Spider train | 5819 | 120 | Общие данные для SFT и GRPO |
| `validation` | Остальные базы Spider train | 956 | 20 | Настройки и выбор итогового чекпойнта |
| `validation_fast` | Подвыборка validation | 200 | 20 | Частые дешёвые проверки во время обучения |
| `test_spider` | Spider dev | 1032 | 20 | Основная финальная оценка проекта |
| `test_bird` | BIRD Mini-Dev без пересечения баз | 427 | 10 | Дополнительная финальная оценка |

`test_spider` — **наш финальный тест на Spider dev**, не официальный Spider test.
Локально есть вопросы официального test, но отсутствуют все его 40 баз данных.
Оценки относятся к нашим отфильтрованным выборкам и функции execution matching,
а не к официальным результатам лидербордов Spider/BIRD.

## Как получено разбиение

1. Берём 140 баз исходного `train_spider.json`, сортируем их имена,
   перемешиваем `random.Random(42)` и резервируем первые 20 под validation.
   Назначение баз фиксируется **до** проверки SQL. Список баз сохранён в manifest.
2. Все вопросы одной базы принадлежат одной основной выборке. У train,
   validation, test_spider и test_bird нет общих `db_id`.
3. BIRD содержит `formula_1`, как и Spider train. Консервативно исключаем из
   BIRD все 66 вопросов этой базы, даже несмотря на отличия DDL файлов.
4. В `validation_fast` выбираем 200 вопросов, перемешивая ID внутри каждой базы
   с seed 42 и обходя базы по кругу. Каждая из 20 баз представлена 10 вопросами.
   Это диагностическая выборка с другим весом баз, не замена полной validation.

Никаких фильтров по правильности ответов Qwen, pass@8, длине генераций или наградам
модели нет. `train_others.json` не используется. Полный train можно проходить не
целиком при ограниченном бюджете; это настройка запуска, а не новое разбиение.
Фактически использованные ID, seed и бюджет должны сохраняться в отчёте запуска.

## Проверка эталонов и исключения

Правила: SQLite read-only, таймаут 5 секунд, максимум 10000 строк.

| Выборка | До фильтрации | Исключено |
|---|---:|---|
| train | 6044 | 216 пустых результатов, 3 ошибки, 6 превышений лимита строк |
| validation | 956 | 0 |
| test_spider | 1034 | 2 превышения лимита строк |
| test_bird | 498 после дедупликации | 66 пересечений по базе, 2 таймаута, 3 превышения лимита строк |

Из 500 исходных BIRD-вопросов загрузчик удаляет 2 дубликата `(db_id, question)`,
сохраняя первое вхождение. ID дубликатов и причины остальных исключений записаны
в manifest. В train пустые эталоны убраны, чтобы не поощрять запросы, всегда
возвращающие пустой результат. В validation остаются 38 пустых эталонов, в
validation_fast — 10, в test_spider — 49; в test_bird их нет. На таких примерах
execution matching может давать ложноположительные совпадения. Наличие пустых
эталонов — ограничение оценки, а не основание исключать их после просмотра метрик.

Эта проверка **не доказывает семантическую правильность всех эталонов**. Она
проверяет возможность вычислить принятую в проекте награду.

## Правила проведения эксперимента

- Только `train` используется для обновления весов SFT/GRPO. Будущий SFT-скрипт
  должен получать данные через `load_split("train")`, как GRPO feasibility.
- Validation используется для выбора настроек и чекпойнта. Старые прогоны
  выбора модели использовали весь Spider train и могли включать эти вопросы:
  validation — данные разработки, не независимое подтверждение качества.
- Сначала фиксируем настройки и выбираем чекпойнты по validation, затем
  сравниваем исходную модель, SFT и GRPO на обоих финальных тестах. Не выбираем
  лучший чекпойнт и не дорабатываем подход по результатам этих тестов.
- Общие условия оценки: один ответ, greedy (`--n 1 --temperature 0`), одинаковые
  промпт, thinking mode, контекст и лимит ответа. Основная метрика — execution
  accuracy; старый sampled pass@1 из model selection оценивает другой режим.
- BIRD содержит дополнительное `evidence`, которое текущий промпт передаёт
  модели. Одинаково используем его для всех сравниваемых чекпойнтов.
- `build_grpo_train.py` теперь только опциональная абляция отбора по модели.
  Её результаты не подменяют общий train основного сравнения.

## Использование на Kaggle

В `DATA_DIR` должны находиться папки `spider/` и `minidev/`, как локально.
Переносим **существующий** `splits/v1.json` вместе с кодом, не создаём его заново.

```bash
DATA_DIR=/kaggle/input/<dataset> python scripts/freeze_splits.py --verify

DATA_DIR=/kaggle/input/<dataset> python scripts/evaluate.py \
  --model Qwen/Qwen3.5-2B --datasets validation_fast \
  --name qwen35_2b_baseline_val_fast

DATA_DIR=/kaggle/input/<dataset> python scripts/evaluate.py \
  --model Qwen/Qwen3.5-2B --datasets validation \
  --name qwen35_2b_baseline_validation
```

Финальная оценка, когда настройки и чекпойнты уже выбраны:

```bash
DATA_DIR=/kaggle/input/<dataset> python scripts/evaluate.py \
  --model Qwen/Qwen3.5-2B --datasets test_spider test_bird \
  --name qwen35_2b_baseline_final
```

Имена папок запусков делаем разными, чтобы не перезаписать предыдущие отчёты.
При ошибке проверки длины увеличиваем общий контекст для всех вариантов;
не удаляем неудобные вопросы из оценки.

Загрузчик проверяет SHA256 исходного JSON и используемых SQLite-файлов. Смена
корня `DATA_DIR` разрешена; изменение содержимого данных вызывает ошибку. Набор
ID не зависит от таймаутов нового компьютера: повторной фильтрации при загрузке
нет. Если ранее принятый эталон теперь не выполняется, оценка останавливается
с ошибкой. Изменения протокола требуют новой явной версии, не перезаписи v1.

Проверки кода без GPU: `python -m unittest discover -s tests -v`.
